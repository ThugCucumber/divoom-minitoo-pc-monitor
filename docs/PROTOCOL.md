# Наблюдения о протоколе MiniToo

Это практические заметки из рабочего проекта, не официальная спецификация Divoom. Часть структуры обмена исследовалась с помощью декомпилированного приложения; затем путь передачи проверялся на устройстве. Само приложение и его исходники здесь не распространяются.

## Bluetooth SPP

Пакет: `01 | length LE16 | command | data | checksum LE16 | 02`.

- `length = len(data) + 3`.
- `checksum = sum(length bytes + command + data) & 0xFFFF`.
- В рабочем пути не применяется экранирование байтов.
- Изображение отправляется командой `0x8B`.

Кадр рисуется 160×128 и кодируется JPEG. Заголовок payload: `23 01 00 00 08 0A`, затем тип JPEG `01`, длина JPEG в четырёх байтах big-endian и сами данные.

Старт передачи: данные `00 + payload_length LE32 + 00`. Payload разбивается на блоки до 256 байт. Каждый блок оборачивается в `0x8B` и содержит `01 + payload_length LE32 + block_index LE16 + block_data`.

Монитор использует один поток чтения Serial: проверяет длину, границы и контрольную сумму пакетов, складывает ответы в очередь. В ответах устройства распознаётся `04 8B`; запрос индекса берётся из байтов `[7:9]`, когда `[6] == 01`.

После передачи всех блоков монитор завершает обмен по ACK `04 8B 55 00 01` либо после 2,2 секунды без новых запросов. ACK наблюдался не на каждом кадре. Дедлайн — 12 секунд, максимум 100 запросов. Неполная передача вызывает закрытие порта и переподключение с паузами 5/10/20/40/60 секунд.

## USB HID

Обнаружение ограничено `VID 4C4A`, `PID 4E55`. В исследованном устройстве джойстик предоставлял Consumer Control HID с трёхбайтовыми input reports:

| Отчёт | Действие |
| --- | --- |
| `00 20 00` | Предыдущая страница |
| `00 10 00` | Следующая страница |
| `00 00 00` | Отпускание |

Повтор одинакового отчёта до изменения состояния подавляется. Выходные HID-отчёты и глобальные клавиатурные перехватчики не используются. Действия вверх, вниз и нажатие по центру в интерфейс проекта не назначены.

## Восстановление процесса

Worker обновляет `monitor_status.json` атомарной заменой файла. Supervisor проверяет его время изменения каждые 5 секунд и завершает worker при отсутствии heartbeat 120 секунд. После выхода worker выдерживается пауза 10 секунд. Во время ожидания следующей минуты часы продолжают обновлять heartbeat.

Обработка закрытия Serial отменяет native read и ждёт поток перед освобождением порта. Если поток не завершился, процесс заканчивается через `os._exit(2)`. Восстановление процесса не гарантирует восстановления зависшей прошивки или самого Bluetooth-устройства.
